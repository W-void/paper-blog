现在的生成式推荐基本都遵循快手定下的范式：SID+NTP+RL，如果要给这三者的重要性排个序，我个人是将SID放在首位的。原因有三：

1. SID最简单，应用场景最广泛。SID说白了就是对emb的量化，下限很低，最容易上手。应用也最广泛，几乎不挑业务也不挑链路，可以直接召回、作为精排的特征、长序列检索等。而NTP可能各种水土不服，比如本地生活场景，用户的行为太离散了，用户进入app前可能受到各种干扰、影响用户决策，我都不知道我中午要吃什么，而且用户在app内停留的时间太短，很难形成稳定的语义决策。可能短视频app更适合NTP范式，因为用户会在一个封闭app内停留较长时间，可能存在稳定的语义决策过程，建模更容易。我觉得一个场景适合NTP的前提是增长序列能来带收益，要是一个业务场景，序列加到300、1000收益就见顶了，靠NTP scaling law肯定没鸟用。

2. SID定义了生成空间，直接限制了GR的上限。如果itemA和B的SID一样，不管NTP和RL怎么迭代，都无法区分这俩item。冲突率肯定会制约个性化。NTP和RL都是锦上添花的，要迭代生成式就绕不开SID。

3. SID的上限也很高。这类SID+NTP+RL的生成式方案，能直接生成target而不像精排那样复杂度和候选有关，所以给大家的想象空间大，这个想象空间毫无疑问就是SID带来的。除此之外，现在都在搞链路对齐，现在这样SID+NTP+RL是不是又人工增加了新的链路呢？能不能直接把NTP（推理）、RL（探索）的思想直接融入SID生成过程中而舍弃掉NTP+RL呢？



现在的论文实在太多了，按我自己的思路整理了下，分为以下两个主要任务。我设想的终态SID可能是冲突率接近0（比如把1层1000个码本，变成10层2个码本，容量上是一样的，利用率不会涨，但共享次数变多了，泛化能力就变强了，再想办法降低冲突率），同时融合了后链路的端到端SID。

- 而腾讯的UniSID反过来了：一般是先得到一个emb再量化（不管emb是llm输出还是直接从精排拿），UniSID认为在生成emb时就已经有目标不一致问题了，所以提出直接从原始广告数据联合生成 SID 和 embedding（SID head在Emb head之前，本文认为emb token 自然聚合了全部广告信息 + 从粗到细的 SID 层级语义，形成一种隐式的"思维链"），然后用SID和emb重建LLM摘要（一般是SID重建emb，本文的SID->emb相当于重建emb了，本文相当于多了一个重建摘要的loss）。感觉。就是个莫比乌斯环，到底是先emb还是先SID。

- 最近出现了一种新的方法DIGER，适合这种情况：如果SID已经构造完成了，你作为下游的NTP方向，该如何调整SID。上游是仅考虑语义信息的SID任务，下游是NTP任务，本文用gumbel噪声连接两个任务。在训练时，用Gumbel softmax代替argmax进行探索，也就是说能调整原本固定的SID；然后提出两种不确定性衰减策略，逐步固定gumble噪声，这样就完成了对原始SID的调整，下游任务就能用新的SID了。

- 与下游任务对齐，就会面临下游任务本身存在的问题，比如：长尾稀疏性。一般认为引入多模态信息会缓解长尾问题，所以基本上都会以LLM的多模态emb作为初始化emb。有一些方法对多模态信息和协同信息进行balance，如：阿里的MMQ引入正交正则化防止多模态专家的坍缩和冗余，京东的SA²CRQ则是直面长尾的问题，对头部物品分配更长的编码以提高区分度，对尾部物品分配更短的编码以增强泛化，基于信息论中的路径熵（path entropy）来动态决定每个物品的编码长度。（p.s.把长尾、冷启的各种思想借鉴到SID的成生中，搞个“迁移学习”应该是大有可为的。)

# 方向二：个性化SID

个性化SID说直白点就是降冲突率、防止码本坍塌。SID对物料空间进行聚类、降维，优势就是比原始的随机hash id泛化性高，缺点就是个性化能力不强，如果两个商品的SID是一样的，那对于所有用户来说，GR都无法区分这两个商品，这也是SID这种生成式范式难以完全替代精排的原因。

- 有很多简单的妥协方案，比如TIGER的方案：SID最后加一个随机id；或者这篇文章，Purely Semantic Indexing for LLM-based Generative Recommendation and Retrieval，不追加非语义 token，而是在 ID 分配时放松"最近聚类中心"的硬约束，允许选择次近甚至更远的聚类中心，只要能避免冲突。
>Purely Semantic Indexing for LLM-based Generative Recommendation and Retrieval

- 更优雅（trick）的方式是“魔改”重构损失，给聚类加一些约束。比如字节MERGE对聚类设置阈值，相似度超过阈值 τ才会匹配成功，用 EMA 更新聚类中心；低于阈值则匹配失败，用 Union-Find 算法将这些物品互相聚类，形成新的聚类中心追加到 codebook；形不成有效聚类的物品回收到数据队列等下一轮。
![](https://files.mdnice.com/user/83179/05a5e8bf-e841-4709-9b72-fe6366cb2fef.png)
>MERGE: Next-Generation Item Indexing Paradigm for Large-Scale Streaming Recommendation


- 其实这些“trick”基本都是【端到端SID】方法中的第二贡献点，比如快手S²GR中的均匀性约束：惩罚距离过近的码字，防止语义坍缩；以及负载均衡：动态调整码字激活概率，避免部分码字闲置。
![](https://files.mdnice.com/user/83179/17c2cf69-043a-4c68-a5f8-48f57e24221e.png)


- 变长SID也是一个方向。比如前面提到的京东SA²CRQ，对头部物品分配更长的编码以提高区分度，直觉是：label越多区分度就越大、能分的就越细；但另一篇文章提出了相反的观念Variable-Length Semantic IDs for Recommender Systems，对热门项目用较短的编码表示，而长尾冷藏物品则获得更长的编码，这是从编码效率的角度考虑的，越浅层的id越通用、热门，越深层的id越个性化、冷门。每一步额外预测一个"是否停止"的概率，决定编码长度；每一步用 Gumbel-Softmax 采样（可微分），取期望码本向量后做残差更新，loss上鼓励更短的编码。
>Variable-Length Semantic IDs for Recommender Systems

- 除了残差、变长，还有其他量化方式上的改进。比如：meta的RPG直接把emb分成m个用乘积量化（OPQ）进行并行量化、阿里的REG4Rec（ICDE26）利用MoE并行生成SID，下游NTP推理时先生成置信度高的SID（并行的码本一般会比RQ长，有信息冗余）；腾讯的HiGR在残差的基础上引入层级对比CRQ-VAE。
![](https://files.mdnice.com/user/83179/e7a5728e-fe12-46d5-949c-87c0b746da3f.png)
> Generating Long Semantic IDs in Parallel for Recommendation
> REG4Rec: Reasoning-Enhanced Generative Model for Large-Scale Recommendation Systems
> HiGR: Efficient Generative Slate Recommendation via Hierarchical Planning and Multi-Objective Preference Alignment

- 还有一个子方向是multi-token，即一对多，一个item会有多个SID。如PCTX将序列上下文也作为SID的一部分。（个人觉得这种方式太复杂了）
