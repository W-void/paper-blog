## 零、背景：生成式推荐的崛起与 SID 的被忽视

过去几年，生成式推荐作为一个独立方向异军突起，吸引了大量关注。它的逻辑很诱人：LLM 靠自回归生成在 NLP 上大获成功，推荐系统为什么不能也用同样的范式？于是一条完整的技术路线逐渐成形：用 SID 把 item 离散化，用 NTP 做序列生成，再用 RL/DPO 做偏好对齐。TIGER、OneRec、OneMall……工业界和学术界都在这条路上快速推进。

在这条路线里，SID 只是一个前置步骤——把 item 变成 token，让后面的生成模型能跑起来。它的设计好不好，似乎不那么重要，反正量化完就交给 NTP 了。真正的主角是生成模型本身：更大的模型、更好的对齐、更强的 Scaling。与此同时，判别式推荐继续沿着自己的路走，比如现在很火的 UniRec：统一特征交叉和序列建模。两条路线并行发展、互不干涉（p.s.也不能说完全互不干涉，起码序列建模是共性）。一个算法团队不得不同时跟进两个迥然不同的方向，迟早得精神分裂。

作为一线算法人，大家都希望这种割裂只是暂时的阵痛，寄希望于以 OneRec 为代表的生成式能够快速统一推荐范式——做大 NTP、做复杂 RL，终究能弥补和判别式的差距。但现在越来越多的人发现，生成式短期内只是大号的召回，阵痛远比想象中的要长。

问题出在哪里？问题在于我们想彻底抛弃旧链路从而拥抱 LLM，步子太大扯到蛋！抛弃经过长期技术迭代的判别式模型，根本就是舍本逐末。根子不在生成模型本身，而在于一个从未被认真追问的问题：**SID，能不能成为统一两者的桥梁？** 当 SID 只被当成生成式流水线中的一个预处理步骤，它就永远只能服务于生成式。但如果 SID 被设计成同时承载判别式与生成式能力的表示，整个格局将截然不同。

这正是我们要做的事。

> 之前我写过一篇SID随笔，提到了SID是我最看重的生成式方向。但当时的思路还是很混乱，也只是总结出端到端和个性化两个SID的主要研究方向。既然精神已被污染，思维已经固化，那么就回到一个最简单的问题：推荐系统中最关键的模块是哪一个？召回or精排？那毫无疑问是精排，基于精排模型无脑堆机器，召回是不是也能解决？所以one model是不是应该从精排模型出发，兼并其他模块？

## 一、道：SID 的本质与 One Model 的使命

### 判别式和生成式，本质上都是在算 argmax

很多人觉得召回和精排是两种范式，统一它们需要设计一套全新的系统。但问题其实比这简单得多——两者本质上都是 argmax，只是作用的空间不同：

- **判别式**：在 item 空间上找最高分 — `argmax_i p(y|f_i, u)`
- **生成式**：在 token 空间上找最高分 — `argmax_t p(s_{1-t}|u)`

生成式解决的不是什么新范式问题，而是一个具体的计算问题：全库几千万 item 做 argmax，代价无法承受，所以才有了多阶段漏斗和所有随之而来的痛点。把 argmax 的空间从 item 换到 token，beam search 的复杂度与 item 总量无关，全库检索天然可行。

> 说个更扎心的话。都在想怎么蹭 LLM 的生成式概念，人家 LLM 是一下生成几十万个 token。GR 呢？一次只生成三、四个 token，算个勾巴生成式。即使是生成列表，也经常会假设可以并行；甚至是只生成一个 item 的 token 时，并行的方案也一直在被提出，NTP 也没有统一江湖。

### SID 的本质：把 argmax 的空间从 item 换到 token

拨开"生成式推荐"的外衣，SID 的本质只有一句话：**把 argmax 的空间从 item 换到 token，让全库 argmax 在工业规模下计算可行。** 它不是为了 Scaling Law，不是新范式，就是解决一个具体的计算问题。

这就是为什么 SID 能成为桥梁：**两边用的是同一套 embedding，同一套 loss，只是 argmax 的空间不同。** 召回和精排的割裂，不是范式割裂，是 argmax 空间的割裂——而 SID 恰好站在两个空间的交叉点上。

近期精排侧的进展也从另一个方向印证了这条路：UIST（2024）将量化 embedding 作为离散 token 引入 CTR 预估；STORE（2025）在精排中引入 Semantic Tokenization，线上 AUC 提升 1.195%；TRM（2026）在搜索与精排中彻底以 semantic token 替代 item ID embedding，已大规模线上部署。召回和精排，从不同路径走向了同一个方向。

### One Model 的正确建设路径

认清这一点，One Model 的建设路径就完全不同了。

不是从头设计一套生成式系统，而是把判别式积累的所有成熟能力迁移到 token 空间上来。**生成式推荐不是判别式推荐的替代者，它是判别式推荐在 token 空间上的自然延伸。** 用生成式的计算结构解锁全库 argmax 的可行性，用判别式的成熟技术保证推荐质量。

![](https://km.sankuai.com/api/file/cdn/2758933682/235504727739?&isNewContent=false&contentType=1)

至于 SID 当前没能承担起这个使命，原因也很清楚：**现有的 SID 只被设计成服务召回，精排的信号从未真正参与码本的构造。** 怎么让精排信号直达码本、哪些信号能编进 SID、编不进去的如何补——这是术要解决的事。

**直观对比：从召回训练 SID vs 从精排训练 SID**

同样是训练 SID，训练信号的来源决定了 SID 能承载的能力边界——也决定了它在全链路上能释放多大的价值：

| 对比维度 | 从召回训练 SID（现有主流做法） | 从精排训练 SID（One Model 路径） |
|---|---|---|
| **训练信号** | NTP loss 为主；重建误差驱动码本 | BCE/BPR 判别式 loss 为主；判别信号端到端穿过量化器 |
| **SID 的区分能力** | item 在 embedding 空间距离近就归同一 token；区分粒度由向量几何决定 | item 在推荐目标上难以区分才被归同一 token；区分粒度由判别式 loss 决定 |
| **用于召回的收益** | 生成路径流畅；但召回的 item 与精排目标往往存在目标不一致 | 召回的 item 已由判别信号筛选过，与精排目标天然对齐；召回质量更高 |
| **用于精排的收益** | 几乎没有——码本和精排的 CTR/CVR 目标无关 | SID 码本边界内化了推荐目标；token 统计特征可直接作为精排特征复用 |
| **冷启动能力** | 依赖内容 embedding 相似度；token 推荐意义有限 | 多模态 side info 保底 + 判别信号精调；冷启动效果更强 |
| **One Model 可行性** | 不可行——SID 只服务生成式，精排仍需另一套独立体系 | 可行——召回和精排共用同一套码本和 token 特征体系 |

一句话概括：**从召回训练 SID，只是把 item 变成 token；从精排训练 SID，才是把推荐能力编进 token。**

> 💡 **就像 LLM 的 aha moment，把量化做对，生成能力自然涌现。**

## 二、术：如何用 SID 统一生成式和判别式

道说清了方向：精排模型作基座，tokenizer 作桥梁，一次训练得到两个模型。对于精排，token-level 相当于正则、dropout，可以增加其稳定性；对于召回，item-level 的端到端指导可以提高其上限。

术要解决的是落地问题。三个术对应三个阶段，**SID 怎么造、信号怎么进、缺口怎么补**——每个阶段都有一个核心矛盾，每个矛盾背后都有一条值得深挖的迭代主线。

### 术一：SID 怎么造——让码本边界服务推荐目标，而不是语义距离

现有 SID 的码本是怎么划的？大部分方法的逻辑是：把 item 的内容 embedding 用 RQ-VAE 量化，内容向量距离近的 item 落入同一个 token 桶。这个逻辑很自然，但问题也很明显：**内容相似 ≠ 推荐效果相似**。两个品类相同的商品，一个对某类用户极具吸引力，另一个完全没吸引力——内容距离很近，推荐决策边界却天差地别。用语义距离划出来的码本，和推荐目标没有直接关系。

所以术一的迭代方向只有一句话：**让判别式 loss 直接驱动码本划分，而不是靠内容重建误差间接影响**。tokenizer 不再是独立预训练的前置步骤，而是内嵌于精排模型端到端训练——精排的 BCE 梯度穿过量化器，码本边界被迫向推荐决策边界靠拢。一旦这件事成立，SID 划分出来的 token 桶就不再只是"内容相似的 item 堆"，而是"在推荐目标上难以区分的 item 堆"——对召回来说，这是本质性的质量提升。

这个方向上可以深挖的点：

- **SID 与 SID embedding 解耦**：现有方法把 SID 的"定址功能"和"语义表达功能"混在一起，量化精度和语义共享之间存在根本 trade-off——SID 划得越细，精准定址越好，但桶间语义共享越少。解耦之后，SID 只负责定址，可学习的 SID embedding 由判别 loss 端到端训练承担表达——两个目标互不干扰，上限都能更高。
- **SID 稳定性**：tokenizer 端到端训练带来一个工程难题——每次模型更新，码本边界可能漂移，同一个 item 的 SID 跨版本不一致，倒排索引失效。稳定性和端到端训练之间的张力是工业落地绕不开的问题。可深挖的方向：encoder 输入只用静态类目特征、离线 Balanced K-Means 树保证零碰撞率、SID 固定后只更新 embedding 等。
- **冷启动保底**：纯判别信号驱动的码本对新 item 几乎无解——没有行为数据，梯度无从传播。加入多模态 side info 作为 encoder 输入，新 item 能凭内容相似性找到已有的 token 桶，冷启动时 SID 就具备了意义。头部 item 靠判别信号精调量化质量，长尾和新 item 靠 side info 保底——两者缺一不可。

### 术二：信号怎么进——划清特征分配边界，把每类信号用在它该在的位置

术一解决了"码本边界由谁塑造"的问题，术二要解决的是"精排的完整特征体系，在 One Model 框架里如何分配"。做过精排的人都清楚，判别模型的效果不靠单一的 item embedding，而靠完整的特征体系：item 特征、user 特征、u2i 交叉特征、上下文特征，四类缺一不可。现在要把精排的能力迁移到 SID 驱动的 One Model 上，**这四类特征哪些能编进 SID，哪些不能，不能的又该怎么处理**——这是整个方法设计的主轴。

核心约束只有一条：**SID 是 item 的固有属性，不依赖特定用户和请求时的上下文**。一个 item 只有一个 SID，它不随用户变化，不随时间变化。这条约束把四类特征天然分成了两组：

- **能无损编入或无损兼顾的**：item 静态特征和全局协同统计可以直接编入 SID encoder；user 特征和上下文特征虽然不能编进 SID，但训练时作为判别 loss 的 condition 参与，推理时同样作为生成模型的 condition 输入——训练和推理两端完全对称，无损。
- **真正有结构性损失的，只有 u2i 交叉特征**：用户对某个具体 item 的历史 CTR、CVR、加购率等，是 user × item 的联合属性，同一个 item 对不同用户的值完全不同——SID 的静态性从根本上截断了这类信号的 item 粒度表达。训练时可以让 u2i 梯度隐式塑造码本边界，但这只影响划分方式，SID 本身携带不了个性化粒度的 u2i 信息。这个缺口，是 One Model 相对于精排的根本性信息代价，也是术三要处理的问题。

这个方向上值得深挖的点：

- **u2i 信号对码本的隐式塑造**：u2i 特征虽然不能编进 SID，但在训练时拼入 scoring MLP，BCE 梯度会携带 u2i 信号反向塑造码本划分——量化器倾向于把"对某类用户行为模式相似"的 item 聚入同一桶，而不是内容相似的 item。这个效果是隐式的，如何设计让它更显式、更稳定，是值得深挖的方向。
- **多任务 loss 的设计**：精排 loss、召回 loss、量化 commitment loss、语义重建辅助 loss……各路 loss 之间如何协调权重、避免梯度冲突，对最终效果影响很大，且场景依赖性强，没有通用答案。
- **逐层监督的必要性**：召回是逐层 beam search，每一层的前缀都要打分。如果只在最后一层加召回 loss，中间层的前缀 embedding 对 MLP 来说是 out-of-distribution 输入，推理时打分失准。逐层加监督能消除训练和推理之间的 discrepancy，但代价是训练复杂度上升——如何在效果和成本之间取得平衡，值得研究。

### 术三：缺口怎么补——推理时最小化 u2i 信息损失

术二确认了 u2i 交叉特征是无法消除的结构性缺口：精排推理时 u2i 特征是 item 粒度的，One Model 召回时 SID 是 item 共享的，两者之间存在不可弥合的粒度差。术三要做的，是**在不改变 SID 静态性的前提下，把推理侧的信息缺口尽量缩小**。

最朴素的做法是统计均值：对每个 token 桶，把桶内所有 item 的 u2i 特征做用户维度的均值，当作该桶对该用户的"等效 u2i"。这做法可以用，但上限很低——粗粒度桶内几百个 item 平均下来几乎对所有用户长一个样，个性化分辨率基本丢失；稀疏用户的统计估计噪声极大，质量更差。

更好的迭代方向是**用模型泛化代替统计归纳**：训练一个轻量级 user-conditioned 网络（MLP_u2t），以用户表示和当前前缀 SID embedding 为输入，在线直接生成 u2t 表征，代替统计均值拼入精排 MLP 打分。本质是把精排 MLP 积累的 u2i 建模能力蒸馏到 token 粒度——对稀疏用户和长尾 item 都更鲁棒，且无需任何离线统计表，线上存储开销为零。

这个方向上可以深挖的点：

- **蒸馏信号的质量**：MLP_u2t 的教师信号是 batch 内实时聚合的统计均值，教师本身就是有噪声的近似——用��个噪声信号来蒸馏，学生能学到多少？如何构造更高质量的教师信号（比如历史版本的离线统计、或精排模型直接输出的 attention 权重），是值得探索的方向。
- **信息缺口的可测量性**：u2i 到 u2t 的信息损失是可以量化的——用 oracle u2i 直接参与 beam search 打分作为上界，MLP_u2t 近似作为下界，两者的 Recall@K 差值就是缺口大小。把这个缺口做成监控指标，可以指导每次迭代是否真的在缩小它，避免"改了很多但缺口没变"的无效迭代。
- **维度对齐原则**：MLP_u2t 的输出维度要显式对齐 u2i 交叉特征的维度，这样精排 MLP 完全不需要改动，召回路径来适配精排——精排零改造，工程接入成本极低。这个原则看起来是实现细节，但决定了 One Model 对存量精排系统的侵入性，工业落地时价值很大。

## 三、小结：术的体系

三个术，各解决一个阶段的核心矛盾，合在一起才是完整的落地路径：

1. **术一（造）**：让码本边界服务推荐目标。tokenizer 不再是独立的预处理步骤，判别 loss 端到端穿过量化器，SID 划分出来的桶对应推荐决策边界而非语义等值面。
2. **术二（进）**：划清特征分配边界。能编进 SID 的编进去，不能编的通过训练 condition 和梯度隐式塑造。唯一有结构性损失的是 u2i 交叉特征——认清这一点，才能把后续的弥补工作做到位。
3. **术三（补）**：最小化推理侧的 u2i 信息缺口。从统计均值到模型蒸馏，本质是把精排积累的 u2i 建模能力迁移到 token 粒度，在不改变 SID 静态性的前提下尽量恢复个性化分辨率。

三个术的逻辑是因果链，不是并列关系：**术一决定了 SID 能承载的信息上限，术二决定了训练时各类信号如何最大化利用，术三决定了推理时不可避免的信息损失如何最小化。** 少了任何一环，整个 One Model 的质量天花板都会被拉低。

三者合力，才能真正实现"Discrimination is Generation"——判别式与生成式不再是两个割裂的世界，而是同一套 token 空间上的两种计算视角。

> 这条路肯定不是最终的路，但至少是更顺滑的路：先统一架构，再缓图 One Model。即使你不是做 One Model 的，只负责精排或召回一段链路，也有动力去尝试 DIG。然后更进一步，**One Model 新范式没准就自 DIG 始了呢**。
