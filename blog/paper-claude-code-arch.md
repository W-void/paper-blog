## 缺口：Agent 工程的"黑盒"困境

在 Claude Code 源码泄漏之前，业界对"地表最强编程 Agent"的内部实现几乎一无所知。大家知道它能用，知道它比其他工具强，但不知道它为什么强——是模型更聪明，还是工程更扎实？

这个问题不是学术问题，而是每个在做 Agent 的工程师都面临的实践困境：我应该把精力放在调模型上，还是放在搭系统上？我的 Agent 为什么会"跑偏"？为什么上下文一长就开始犯蠢？为什么自我评估总是过于乐观？

Claude Code 的 51 万行源码，提供了一份来自"最强实践者"的答案。这篇文章的价值，就是把这份答案从代码翻译成可以直接借鉴的工程原则。

## 增量：80% 的代码在死磕可靠性，不是在让 AI 更聪明

**这篇文章让我们知道了什么以前不知道的？**

Claude Code 的核心竞争力不是模型能力，而是一套精密的"缰绳系统"——四层架构 + Tool-Use Loop + 动态 System Prompt + 四类型记忆 + 五步上下文压缩，每一个组件都在解决一个具体的可靠性问题，而不是在让模型"更聪明"。

## 核心机制

### 一、四层架构：职责分离的基础

```
┌─────────────────────────────────────────────────────────┐
│  引擎层（Engine）                                        │
│  大脑：协调 + 分发 + 决策                               │
│  原则：不包含任何业务逻辑，只做三件事                    │
│    ① 拼上下文发给大模型                                  │
│    ② 大模型说"用工具"时找到工具并执行                   │
│    ③ 根据返回决定继续循环还是结束                        │
├─────────────────────────────────────────────────────────┤
│  工具层（Tools）                                         │
│  能力：40+ 个工具，每个工具强制声明三个安全属性          │
│    ① 只读 or 会改东西？                                  │
│    ② 破坏性操作需要额外确认？                            │
│    ③ 能否与其他工具并发执行？                            │
│  类型系统强制要求，漏掉任何一个编译不过                  │
├─────────────────────────────────────────────────────────┤
│  服务层（Services）                                      │
│  基础设施：大模型 API 调用 + 上下文压缩 + MCP 协议       │
│  所有层共享，像大楼的水电煤                              │
├─────────────────────────────────────────────────────────┤
│  安全与治理层（Security & Governance）                   │
│  安全网：罩在所有层上面                                  │
│    ① 权限系统：哪些操作需要确认，哪些自动执行            │
│    ② Hook 系统：工具执行前后插入自定义行为               │
│    ③ Bash 安全模块：语法级分析，不是正则匹配关键词       │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：工具层的三个安全属性是类型系统强制要求的，不是"建议加上"的。每一把刀从出厂就配好了刀鞘。

### 二、Tool-Use Loop：比 ReAct 更简洁的 Agent 范式

Claude Code 没有用 ReAct（Thought-Action-Observation 三步循环），而是用了一个更简洁的 Tool-Use Loop：

```
while (true) {
    ① 压缩上下文（五步从轻到重）
    ② 调用大模型 API，流式接收
    ③ 分析模型返回：
       - end_turn → break（任务完成）
       - tool_use → 执行工具，把结果拼入消息列表，continue
}
```

**为什么比 ReAct 更好？**

ReAct 是为"弱模型"设计的——用显式的 Thought 步骤引导模型一步步推理。但 Claude Opus 支持 Extended Thinking（模型在内部完成推理，不占用应用的上下文空间），Claude API 原生支持 tool_use 类型响应（不需要解析文本提取 Action），end_turn 是 API 层面的原语（不需要检测"Final Answer"字符串）。

结果是：推理交给模型，执行交给工具，编排交给最简单的 while(true) 循环。

**Plan Mode**：在同一个 Tool-Use Loop 中，通过 EnterPlanMode 和 ExitPlanMode 两个工具实现"先规划再执行"的两阶段工作流。进入 Plan Mode 后权限降为只读，每 5 轮对话系统会给模型塞一张"小纸条"提醒它不要手痒改代码。这个设计的精妙之处是"工具即能力"——Plan Mode 不是特殊的模式切换，只是调用了两个工具，引擎层完全不需要做任何特殊处理。

### 三、System Prompt 的构造：动态组装 + 三级缓存

System Prompt 不是静态文本，而是由十几个 Section 动态拼接而成，核心内容包括：

**角色定义与安全红线**：定位为"interactive agent"而非"assistant"，立刻划安全红线（不能乱编 URL）。安全约束用"先肯定再约束"的写法（先说可以做什么，再说不能做什么），比纯禁止清单效果好得多。

**行为准则（最值得抄作业的部分）**：
- 修改代码前先阅读：不对没读过的代码提修改建议
- 少即是多：不在用户要求之外添加功能、重构代码、创建辅助函数
- 先诊断再换方案：失败后先搞清楚为什么失败，不盲目重试也不草率放弃

**操作安全**：用"可逆性"和"影响范围"两个维度判断风险，而不是笼统的"危险/安全"二分法。关键补充：用户批准了某个操作一次，不代表在所有场景下都批准——授权仅对指定范围有效。

**工具使用指南**：读文件用 Read 工具而不是 cat，编辑用 Edit 工具而不是 sed。原因不只是体验，更是安全——专用工具有专用的权限检查，Bash 命令没有这层保护。

**Git 安全协议**：绝不修改 git config，绝不跳过 hooks，绝不 force push 到 main/master。特别值得注意的一条：pre-commit hook 失败时 commit 实际上没发生，这时候 --amend 会修改上一个不相关的 commit，可能导致代码丢失。正确做法是修复问题后创建新的 commit。

**输出风格约束**：工具调用之间的文字不超过 25 个词，最终回复不超过 100 个词。极度苛刻，目的是避免 Agent"话痨"。

**三级缓存体系**：

```
┌─────────────────────────────────────────────────────────┐
│  分割线之上（所有用户完全一样）                           │
│  角色定义 / 安全红线 / 行为准则 / 操作安全 / Git 安全    │
│  → 全球所有用户共享同一份缓存，API 费用降低 90%          │
├────── __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ ────────────────┤
│  分割线之下（每个用户不同）                              │
│  环境信息 / CLAUDE.md / 记忆指令 / MCP 指令              │
│  → 实时生成，无法共享缓存                                │
└─────────────────────────────────────────────────────────┘
```

三级缓存：全局缓存（跨组织跨用户）→ 组织缓存（同组织跨会话）→ 会话缓存（同 Section 在一次会话内只计算一次）。

### 四、记忆系统：四类型 + 索引按需加载 + Sonnet 当秘书

**记什么（四类型封闭集合）**：

```typescript
export const MEMORY_TYPES = [
  'user',      // 用户画像：角色、偏好、知识水平
  'feedback',  // 行为反馈：该做什么、不该做什么（必须记 Why 和 How to apply）
  'project',   // 项目动态：在做什么、截止日期（相对日期必须转成绝对日期）
  'reference', // 外部指针：去哪找什么信息
]
```

**不记什么（排除清单）**：代码模式、项目架构、文件结构（用 grep/git 获取）、Git 历史（git log 是权威来源）、CLAUDE.md 里已有的内容（避免重复）、临时任务状态。核心原则：**可以从当前代码推导出来的信息，一律不存**——代码是"活的"，记忆是"死的"，存了会变成"权威的错误"。

**怎么存（索引 + 独立文件）**：每条记忆存为独立的 .md 文件（含 YAML frontmatter：name、description、type），MEMORY.md 作为不超过 200 行的轻量索引。索引始终加载到 System Prompt，独立文件按需加载。

**怎么召回（Sonnet 当秘书，三步走）**：

```
① 扫描所有记忆文件的前 30 行（只读 frontmatter，不读全文）
② 把所有记忆的 description 清单 + 用户当前输入发给 Sonnet
   → Sonnet 返回最相关的 5 个文件名（max_tokens=256，极短）
③ 加载选中记忆的完整内容，注入上下文
   → 超过 1 天的记忆自动附加陈旧度警告
```

**并行预取**：Sonnet 侧查询在用户提交消息后立刻启动，和主模型 API 调用并行执行。Sonnet 比 Opus 快得多，等主模型响应回来时记忆选择早就完成了，几乎不增加额外延迟。

### 五、上下文压缩：五步从轻到重

核心哲学：**压缩一定有信息损失，所以能不压就不压，必须压的时候从最轻的手段开始。**

```
层级    手段              信息损失    API开销    触发条件
第1层   大结果存磁盘      几乎为零    零         工具结果超 50KB
第2层   砍掉远古消息      低          零         消息过时
第3层   清理老工具输出    中低        零         缓存过期/数量超限
第4层   读时投影压缩      中          低         上下文达 90%
第5层   全量摘要          高          高         上下文达 ~93%
```

**第1层（大结果存磁盘）**：工具结果超 50KB 就存磁盘，消息里只留 2KB 预览。完整内容没有丢，模型需要时可以重新读取特定行范围。

**第2层（砍掉远古消息）**：直接移除对话开头的老消息，插入边界标记。不做摘要，零 API 开销。会把释放的 Token 数传给第5层，避免重复压缩。

**第3层（清理老工具输出）**：只清理"可重新获取"的工具结果（Read/Bash/Grep/Glob），AgentTool（子 Agent 输出）永远不清理——子 Agent 的推理过程不可重复。触发条件：距上次 API 调用超过约 60 分钟（Prompt Cache 大概率已过期）。

**第4层（读时投影）**：不修改原始消息，只在调用 API 的那一刻动态计算压缩视图。触发阈值：90% 上下文窗口开始压缩，95% 紧急压缩。如果第4层够用，第5层就不触发。

**第5层（全量摘要）**：触发阈值约 93% 上下文窗口（有效窗口 - 13K 缓冲区）。摘要按多个维度结构化生成（用户意图、关键技术概念、涉及文件、错误和修复、待完成任务、当前状态、建议下一步）。**压缩后恢复**：从文件状态缓存中找出最近访问的文件（最多5个、总计不超过50K Token）重新注入，让模型无缝继续工作。连续失败3次自动放弃（熔断器模式）。

## 费曼讲解：三个关键概念

### 概念一：读时投影（Read-Time Projection）

想象你有一本 500 页的工作日志，但每次开会只能带 50 页进去。

"写时压缩"的做法是：在开会前把日志剪掉，只保留 50 页，剩下的扔掉。这样日志本身变短了，但信息也永久丢失了。

"读时投影"的做法是：日志还是 500 页，但开会时你只带一份"摘要版"进去。原始日志完好无损，下次开会可以带不同的摘要版。

Claude Code 的第4层压缩就是读时投影——原始消息列表不变，只在发给 API 的那一刻动态生成一个压缩视图。这样如果压缩不够用，还可以换一种压缩策略重试，而不是在原始数据上做了不可逆的修改。

### 概念二：陈旧度检测（Memory Freshness）

记忆是某个时间点的观察，不是实时状态。

用户 30 天前存了一条记忆："AuthService 在 src/auth.ts 第 42 行使用了 JWT"。但代码早就重构了，这条记忆现在是错的。如果模型盲目相信它，就会给出错误的建议。

陈旧度检测的做法是：超过 1 天的记忆自动附加警告——"这条记忆已经有 N 天了，其中关于代码行为或 file:line 引用的断言可能已经过时，在当作事实引用之前请先对照当前代码验证。"

这个机制的本质是：记忆系统主动承认自己的局限性，而不是假装自己是权威来源。

### 概念三：工具即能力（Tools as Capabilities）

Plan Mode 的实现方式揭示了一个重要的设计哲学：不要用"模式切换"来改变 Agent 的行为，而是用"工具"来改变。

如果用模式切换，引擎层需要知道"现在是 Plan Mode，所以要限制权限"，这意味着引擎层包含了业务逻辑，违反了四层架构的分离原则。

如果用工具，EnterPlanMode 工具执行时降低权限，ExitPlanMode 工具执行时恢复权限，引擎层完全不需要改动。新增任何"模式"只需要新增两个工具，系统的其他部分完全不受影响。

## 启发：这篇文章照亮了什么盲区

**对 autoresearch skill 的直接启发**：

autoresearch 的记忆系统目前是扁平的——什么都往里存，没有类型约束，没有排除清单。Claude Code 的四类型封闭集合 + 排除清单是一个值得借鉴的设计：强制分类让 Agent 做分类决策，排除清单防止记忆膨胀成垃圾堆。

**对上下文管理的启发**：

"读时投影"这个概念很有价值。目前很多 Agent 的上下文压缩是破坏性的（直接修改消息列表），而读时投影是非破坏性的（原始数据不变，只在发给 API 时生成压缩视图）。这个思路可以让压缩策略更灵活，也更容易调试。

**对 System Prompt 设计的启发**：

"先肯定再约束"的写法（先说可以做什么，再说不能做什么）比纯禁止清单效果好得多。"可逆性 + 影响范围"两个维度判断操作风险，比笼统的"危险/安全"二分法精细得多。这两个原则可以直接用到任何 Agent 的 System Prompt 设计中。

**一个值得追问的问题**：

文章提到 Sonnet 当秘书做记忆检索，用的是 description 字段做相关性匹配。但 description 是存记忆时手动写的，质量参差不齐。能不能在存记忆时，让 Sonnet 自动生成一个高质量的 description？这是一个"存时优化"vs"取时优化"的权衡问题。
