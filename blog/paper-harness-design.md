## 缺口：两个顽固的天花板

长时间运行的 Agentic 编程任务，在 2025 年已经有了一套基本可用的 harness 框架：用初始化 Agent 把需求拆成任务列表，再用编码 Agent 逐特性实现，通过结构化 artifact 在 session 之间传递上下文。这套框架把 Claude 的表现推到了远高于 baseline 的水平——但随后撞上了两堵墙。

**第一堵墙：上下文焦虑（Context Anxiety）。** 随着 context window 填满，模型开始失去连贯性。更糟糕的是，某些模型（Sonnet 4.5 尤为明显）会在接近它认为的上下文上限时提前收尾，把工作草草了结。Compaction（就地压缩历史对话）能缓解这个问题，但无法根治——因为 Agent 仍然知道自己在一个"很长的对话"里，焦虑感依然存在。真正的解法是 **Context Reset**：彻底清空上下文，启动一个全新的 Agent，通过精心设计的 handoff artifact 把前一个 Agent 的状态和下一步任务传递过去。代价是更高的编排复杂度、token 开销和延迟。

**第二堵墙：自我评估偏差（Self-Evaluation Bias）。** 让 Agent 评估自己刚写完的代码或设计，它几乎总是给出过于乐观的评价——即便人类一眼就能看出质量平庸。这个问题在主观任务（如前端设计）上尤为突出，因为没有像单元测试那样的二元验证机制。即便是有可验证结果的编程任务，Agent 也常常在发现问题后说服自己"这不是大问题"然后放行。

这两个问题，就是这篇文章要解决的核心缺口。

## 增量：GAN 启发的 Generator-Evaluator 分离架构

**这篇文章让我们知道了什么以前不知道的？**

把 GAN（生成对抗网络）的"生成器-判别器"结构搬到 Agentic 系统里，可以系统性地解决自我评估偏差问题，并在此基础上构建出能运行数小时、产出完整全栈应用的三 Agent 架构（Planner + Generator + Evaluator）。

关键洞察有两层：

1. **主观质量可以被操作化**。"这个设计好看吗？"无法稳定评分，但"这个设计是否符合我们定义的四条标准？"可以。把审美判断转化为可评分的标准，是让 Evaluator 能够工作的前提。

2. **独立 Evaluator 比自我评估更容易调教**。Evaluator 作为独立 LLM，天然也倾向于对 LLM 生成的内容宽容——但把它调教成"挑剔的 QA 工程师"，比让 Generator 对自己的工作保持批判性要容易得多。一旦外部反馈存在，Generator 就有了具体的迭代目标。

## 核心机制

### 前端设计实验：让主观质量可评分

```
用户 Prompt
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Generator Agent                                        │
│  输入：用户 Prompt + 四条评分标准                         │
│  输出：HTML/CSS/JS 前端实现                              │
└─────────────────────────────────────────────────────────┘
    │  生成的前端页面
    ▼
┌─────────────────────────────────────────────────────────┐
│  Evaluator Agent（配备 Playwright MCP）                  │
│  行为：自主导航页面、截图、交互                           │
│  输出：四维评分 + 详细批评                               │
│  四维标准：                                              │
│    ① Design Quality（设计整体感）                        │
│    ② Originality（原创性，惩罚 AI 套路）                 │
│    ③ Craft（技术执行质量）                               │
│    ④ Functionality（可用性）                             │
│  权重：① ② > ③ ④（Claude 默认在③④已够好）              │
└─────────────────────────────────────────────────────────┘
    │  评分 + 批评反馈
    ▼
Generator 收到反馈后做战略决策：
  - 分数趋势良好 → 在当前方向上精炼
  - 方向不对 → 完全转向，尝试不同审美风格
    │
    └─── 循环 5-15 次，直到收敛或达到上限
```

**关键细节**：
- Evaluator 用 few-shot 示例校准，确保评分与作者偏好对齐，减少跨迭代的分数漂移
- 评分标准的措辞本身就在引导 Generator（"最好的设计是博物馆级别的"这句话会让设计向特定风格收敛）
- 分数提升不是线性的，有时中间某次迭代比最终版本更好
- 荷兰艺术博物馆案例：第 9 次迭代是精致的深色主题页面，第 10 次突然转向——用 CSS perspective 渲染 3D 展厅，画作挂在墙上，用"门"导航不同展厅。这种创意跃迁在单次生成中从未出现过。

### 全栈编程：三 Agent 架构

```
用户（1-4 句话的简短 Prompt）
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Planner Agent                                          │
│  输入：简短 Prompt                                       │
│  输出：完整产品规格（高层次，不含实现细节）               │
│  原则：                                                  │
│    - 野心勃勃地扩展范围                                  │
│    - 聚焦产品上下文和高层技术设计                        │
│    - 不指定实现细节（避免错误级联）                      │
│    - 主动织入 AI 功能                                    │
│    - 可调用 frontend design skill 生成视觉设计语言        │
└─────────────────────────────────────────────────────────┘
    │  产品规格文档
    ▼
┌─────────────────────────────────────────────────────────┐
│  Sprint 合同谈判（Generator ↔ Evaluator）                │
│  Generator 提议：这个 Sprint 要做什么、如何验收           │
│  Evaluator 审查：确认方向正确                            │
│  通信方式：文件读写（一方写，另一方读并回应）             │
└─────────────────────────────────────────────────────────┘
    │  Sprint 合同（具体实现细节 + 可测试的验收标准）
    ▼
┌─────────────────────────────────────────────────────────┐
│  Generator Agent（按 Sprint 工作）                       │
│  技术栈：React + Vite + FastAPI + SQLite/PostgreSQL      │
│  工具：git 版本控制                                      │
│  每个 Sprint 结束后自我评估，然后交给 QA                 │
└─────────────────────────────────────────────────────────┘
    │  运行中的应用
    ▼
┌─────────────────────────────────────────────────────────┐
│  Evaluator Agent（配备 Playwright MCP）                  │
│  行为：像真实用户一样点击应用                            │
│  测试范围：UI 功能、API 端点、数据库状态                 │
│  评分维度：产品深度、功能性、视觉设计、代码质量           │
│  机制：每个维度有硬性阈值，任一不达标 → Sprint 失败      │
│  输出：具体 bug 报告 + 改进建议                          │
└─────────────────────────────────────────────────────────┘
    │  失败 → 反馈给 Generator 修复
    │  通过 → 进入下一个 Sprint
    └─── 循环直到所有 Sprint 完成
```

**Evaluator 调教的重要性**：开箱即用的 Claude 是糟糕的 QA Agent。早期测试中，它会发现真实问题，然后说服自己"这不是大问题"然后放行。调教过程是：读 Evaluator 的日志 → 找到它的判断与作者判断分歧的案例 → 更新 QA prompt → 重复。经过多轮迭代，Evaluator 才达到可用水平。

### Harness 迭代：剥离不再必要的组件

随着模型能力提升（Sonnet 4.5 → Opus 4.5 → Opus 4.6），harness 的某些组件变得不再必要：

```
Sonnet 4.5 时代的 Harness：
  Initializer → [Coding Agent + Context Reset] × N → Artifacts

Opus 4.5 时代的 Harness（本文第一版）：
  Planner → [Generator + Sprint Contract + Evaluator] × N → App
  （Context Reset 仍然需要）

Opus 4.6 时代的 Harness（本文第二版）：
  Planner → Generator（连续运行 2+ 小时）→ Evaluator（单次）→ 修复循环
  （Sprint 结构移除，Context Reset 移除，SDK 自动 Compaction 处理上下文增长）
```

**核心原则**：harness 的每个组件都编码了一个关于"模型做不到什么"的假设。这些假设值得定期压力测试——因为它们可能本来就是错的，也可能随着模型进步而过时。

## 费曼讲解：三个关键概念

### 概念一：Context Anxiety（上下文焦虑）

想象你在写一篇很长的报告，但你的稿纸只有 100 页。当你写到第 80 页时，你开始担心写不完，于是开始草草收尾，把原本要详细展开的内容压缩成一句话。

LLM 的 context window 就是这张稿纸。当 context 快满时，某些模型会"感知"到这个限制，开始提前收尾——即便任务还远没完成。这就是 context anxiety。

**解法**：Context Reset。不是压缩稿纸（Compaction），而是换一张新稿纸，同时附上一份"工作交接单"，告诉新 Agent 之前做了什么、接下来要做什么。代价是交接单必须足够完整，否则新 Agent 会迷失。

### 概念二：Sprint Contract（Sprint 合同）

产品规格是高层次的用户故事（"用户可以拖拽时间轴上的片段"），但代码实现需要具体的技术决策（"拖拽事件绑定在哪个 DOM 元素上？状态存在哪里？"）。

Sprint 合同是填补这个鸿沟的机制：在写任何代码之前，Generator 和 Evaluator 先就"这个 Sprint 要做什么、怎么算做完"达成一致。Generator 提议，Evaluator 审查，两者通过文件读写来回协商，直到达成共识。

这样做的好处是：Evaluator 在测试时有明确的验收标准，不会因为"这个功能规格里没说清楚"而产生争议。Sprint 3 的合同有 27 条验收标准，每条都具体到可以直接写测试用例。

### 概念三：Evaluator 校准（Calibration）

Evaluator 是 LLM，天然倾向于对 LLM 生成的内容宽容。要让它变成一个挑剔的 QA 工程师，需要：

1. **Few-shot 示例**：给它看"这种情况应该打多少分、为什么"的具体例子，让它的评分标准与你的偏好对齐
2. **迭代调教**：读 Evaluator 的日志，找到它的判断与你的判断分歧的案例，更新 prompt，重复
3. **硬性阈值**：不是"综合分数达到 X 就通过"，而是"每个维度都必须达到阈值，任一不达标就失败"——这防止了 Evaluator 用某个维度的高分来掩盖另一个维度的严重问题

## 餐巾纸速写：思想框架的位移

```
以前大家这么想：
┌─────────────────────────────────────────────────────────┐
│  Agent = 一个能力全面的 LLM                              │
│  质量控制 = 让同一个 Agent 自我检查                      │
│  长任务 = 压缩上下文，让 Agent 继续跑                    │
│  评估 = "你觉得自己做得怎么样？"                         │
└─────────────────────────────────────────────────────────┘

这篇文章说应该这么想：
┌─────────────────────────────────────────────────────────┐
│  Agent = 专职角色（Planner / Generator / Evaluator）     │
│  质量控制 = 独立 Evaluator，用可操作化的标准评分         │
│  长任务 = Context Reset + 精心设计的 handoff artifact    │
│  评估 = "你来测试这个你没有参与构建的应用"               │
│                                                          │
│  核心位移：                                              │
│  "让一个 Agent 做所有事" → "让专职 Agent 做专职事"       │
│  "主观质量无法评分" → "主观质量可以被操作化为标准"       │
│  "harness 越复杂越好" → "harness 应该随模型进步而精简"   │
└─────────────────────────────────────────────────────────┘
```

## 博导审稿

**选题眼光**：问题是真实的。自我评估偏差和 context anxiety 是 2025-2026 年 Agentic 系统的两个核心痛点，不是人造缺口。把 GAN 的结构类比搬到 Agent 系统里，是一个有洞察力的跨域迁移。

**方法成熟度**：这是一篇工程博客，不是学术论文，所以"方法"更多是工程实践的总结而非理论推导。但工程实践本身是扎实的：有具体的架构图、有量化的成本数据（$9 vs $200，$124 的详细分解）、有真实的 bug 案例（FastAPI 路由匹配问题、LevelEditor.tsx 第 892 行的条件判断错误）。这些细节说明作者真的跑过这些实验，不是纸上谈兵。

**实验诚意**：没有严格的 A/B 测试，没有统计显著性检验——但这是工程博客的正常形态。作者诚实地承认了局限：分数提升不是线性的，有时中间迭代更好；Evaluator 仍然有盲区，深层嵌套的 bug 会漏掉；Claude 听不见声音，所以 DAW 的音乐质量 QA 效果有限。这种诚实是加分项。

**写作功力**：结构清晰，从问题到方案到迭代，叙事逻辑流畅。荷兰艺术博物馆的案例是全文最生动的段落，把抽象的"创意跃迁"具象化了。附录里的 RetroForge 规格文档是很好的补充，让读者能感受到 Planner 的实际输出质量。

**一句话判决**：**Strong Accept**。这是 Anthropic 工程团队在 Agentic 系统设计上最有实践深度的一篇文章，对任何在做 Agent harness 的工程师都有直接参考价值。

## 启发：这篇文章照亮了什么盲区

**对 autoresearch skill 的直接启发**：

autoresearch 的核心循环是"改代码 → 测试 → 保留/丢弃"，这和 Generator-Evaluator 循环在结构上是同构的。但目前 autoresearch 的"评估"部分主要依赖可量化的指标（测试分数、benchmark 结果），对于那些指标不够完善的任务，评估质量会下降。

这篇文章提供了一个补充思路：**把评估标准操作化**。即便是"代码质量好不好"这种主观判断，也可以被分解成若干可评分的维度（可读性、模块化程度、错误处理完整性等），然后用独立的 Evaluator Agent 来评分。

**对 harness 设计的普适原则**：

"harness 的每个组件都编码了一个关于模型做不到什么的假设，这些假设值得定期压力测试"——这句话值得贴在每个做 Agent 系统的工程师的显示器上。随着模型进步，昨天必要的脚手架今天可能是累赘。定期做"减法实验"（移除一个组件，看性能是否下降）是维护 harness 的好习惯。

**对 Sprint Contract 机制的启发**：

在任何需要"生成"和"验证"分离的场景里，Sprint Contract 的思路都适用：在执行之前，让执行者和验证者先就"什么叫做完"达成一致。这个机制的本质是把隐式的验收标准显式化，减少事后争议。

**一个值得追问的问题**：

文章提到 Evaluator 的调教需要"读日志 → 找分歧 → 更新 prompt → 重复"的人工迭代。这个过程本身能不能自动化？能不能用另一个 Agent 来分析 Evaluator 的日志，自动识别它的判断偏差，并生成 prompt 更新建议？这是一个有趣的元层次问题。
